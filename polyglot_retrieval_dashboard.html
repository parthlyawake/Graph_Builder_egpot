01

Build and inspect

We reused the corrected graph snapshots for the listed repositories. Each expected source file was checked against the source and confirmed as a graph retrieval candidate.

02

Ask 21 questions

Three issue-like questions per application, including two cases that require two files. Each application was searched separately, so unrelated products did not compete.

03

Rank distinct files

Every method got the same query and 2,048-token context budget. We collapsed repeated function nodes into distinct files and checked the first 10 files against the labels.

Why seven scored corpora? The eighth listed checkout, Sock Shop, contains deployment and dashboard code rather than its service implementations. We ran two dashboard smoke queries, but kept them out of the application comparison.

File Recall@10 by application, using three queries in each. Small per-repository samples are useful for spotting failures, not estimating production accuracy.

For AWS Retail, R3 recovered the Redis checkout repository file at rank 2, while R1 and R2 missed it. Use the query explorer to inspect both cases.

05 / Interpretation

What these results
cannot prove.

01Small, curated labels

The 21 application questions came from inspected source examples. They are not held-out, independently reported issues. A paper claim needs a larger blinded issue set.

02Signals not present

These source snapshots have no Git history, and no runtime traces were supplied. R8 and R10 ran, but their extra lineage and trace signals were not evaluated.

03Source coverage

DeathStarBench's C++/Thrift services and OpenTelemetry's Rust shipping service are outside current parsing coverage. Sock Shop's service code lives in separate repositories.

04File-level product work

The retriever scores graph nodes and this benchmark collapses them into files afterward. A production affected-file API should score files directly and preserve evidence paths.
